The six core functional requirements

3D volumetric rendering across the full water column, with depth-slice views, isosurface extraction and time-step animation, using WebGL / Three.js or Cesium.js Met

Built on Three.js and WebGL2: a volume you can slice by depth, cut with an isosurface and play through time, with ocean currents in the same block.

  • Isosurface. Named for what it cuts: an isotherm (temperature), an isohaline (salinity) or an isopycnal (density).
  • Currents. Copernicus Marine's own analysis at one twelfth of a degree, drawn as arrows on the depth you slice to and coloured by speed.
  • Real numbers. The speed under the cursor is read from the data, not from the picture.
  • No login for viewers. A free Copernicus account is used once, when the data is baked, and never in the browser.

Multi-format ingestion: NetCDF via an xarray backend, and delimited text formats, with new sources added with minimal code change Met, and you can check it yourself

NetCDF, CSV and the glider index are all read today, and you can test it by dropping your own NetCDF file on the platform.

Formats read

  • NetCDF. Through xarray and netCDF4.
  • CSV. The column layout is stored as data, not code.
  • Glider index. Columns are read from the file's own header, not by position.

Check it yourself

  • Drop a file. Drag a CF-conventions NetCDF file onto the Your own data panel. Its variables join the Variable selector and use the same colourbar, depth slice, isosurface and 3D view as everything else.
  • Same interface. It is read by a Source Adapter exactly like INCOIS, Argo and Copernicus.
  • Clear refusals. A file it cannot read names the problem and draws nothing: no longitude, a sigma-level vertical axis, an ensemble dimension, or an ocean somewhere else in the world.

Limit File upload needs the API running, like OPeNDAP and WMS. The demo itself runs without it.

Customizable colorbar: palette, min/max range, log/linear scale; variable selector; layer opacity control; vertical exaggeration slider Met

Every part of the clause is a control you can use.

  • Range. Two handles. Water outside the range is not drawn at all, so narrowing it is analysis, not decoration.
  • Log or linear. One curve in one file drives both the water and the legend, so they cannot disagree. It was cut once, when they did.
  • Palette. Each variable opens on the cmocean scale designed for it, with a few alternates of the same kind, named by their colours and never by a quantity.
  • Variable selector. Five groups, most computed here: INCOIS publish two quantities and the platform derives many more from them.
  • Opacity and exaggeration. Each has its own slider, because changing how see-through the water is and stretching the depth are different things.

Extensible design for CTDs, moorings, HF-radar, ADCP and machine-learning derived products Moorings met, the rest answered

Moored buoys are already added through the same design. HF-radar and ADCP need a data request to INCOIS, and machine learning is left out on purpose.

  • Moorings, done. NOAA's public GTS feed: a different format (depth instead of pressure, one row per level, no quality flags) behind the same interface.
  • HF-radar and ADCP. INCOIS lists HF-radar data as registered access and moored-buoy currents as view-only, so using either needs a data request to INCOIS. A data-policy limit, not a design gap.
  • Machine learning, refused. Thirty-six analyses is not a training set, and a gap-filler would paint believable temperature over water nobody measured, which this platform shows honestly instead.

Tools that enable intuitive and rapid understanding of three-dimensional ocean phenomena Met, and not asked for

Draw a line on the water and get a vertical section, the standard figure of physical oceanography, cut live beside the 3D block.

  • What you see. Depth down, distance across, the variable as colour.
  • With the instruments. Every float cast within 150 km of the line, each drawn to the depth it actually reached.
  • Real values. Cut from the model's own grid on its own 24 levels, never from the stretched rendering volume, because a reader takes metres off one axis and a value off the colour.
  • Works offline. The three variables an instrument measures ship full-precision grids in the build. /api/section serves the same cut to other tools.

The absence of such a system impedes timely ... climate monitoring Met

Two views of "warmer": against this year's own average, and against the 30-year normal.

  • Temperature Anomaly. Departure from the mean of this build's 36 analyses (August 2025 to July 2026), so mostly the seasonal swing. The panel beside it says so.
  • Temperature vs Normal. Departure from NOAA's World Ocean Atlas 2023 1991-2020 mean for the same calendar month. This is what a forecaster means by "warmer than usual".
  • No regridding. The atlas sits on exactly INCOIS's grid points. If that ever stops being true, the platform refuses rather than regrids.
  • Open access. Read anonymously over OPeNDAP at bake time, with no account.

Limit Below 1500 m the atlas has no normal, so the field is blank there, not zero.

The absence of such a system impedes timely hazard assessment, search-and-rescue support, fishery advisories and climate monitoring Search and rescue: built, and scored

Drop a pin and see where the ocean current alone would carry something, with the error of that prediction published.

  • What it does. Carries the pin forward through the Copernicus current field, at the depth you slice to.

Tools for intuitive, rapid understanding: where does the model disagree with the instruments? Met, and not asked for

Every instrument coloured by how far the model sat from it, so the worst disagreements are found at a glance instead of by clicking instruments one at a time.

  • Ranked. Worst first, on the gap as a fraction of each variable's own range, so degrees and PSU share one list.

  • Not AI. No model, no training set, no confidence score. Every figure is a mean or root-mean-square of gaps already measured.

Open standards (OGC WMS/WCS, CF Conventions for NetCDF) WMS, OPeNDAP and CF met; WCS declined with the reason

The model's data can be pulled out through three open standards. WCS is declined, and the reason is below.

  • Served. OGC WMS 1.3.0, DAP2 OPeNDAP and CF-1.8 NetCDF, all from the native analysis grids, so a consumer gets the same numbers the platform reports.
  • Axis order tested first. WMS 1.3.0 reads EPSG:4326 latitude-first and CRS:84 longitude-first. A mix-up would silently draw the map flipped north to south.
  • Real clients. The OPeNDAP and WMS endpoints are tested with pydap and owslib, not against our own bytes.
  • Every advertised layer can be drawn. Some variables are one number per location rather than a water column, like the depth of the 26 °C isotherm. Those go out with no depth axis and no depth picker, because a depth axis on a variable whose value is a depth would be well-formed and false.
  • WCS, declined. No pure-Python WCS server fits this API (THREDDS is Java, EOxServer runs on MapServer), and the same coverages are already on OPeNDAP.
